1. Extract the viewer's navigation machine

Strong

Files: viewer/RepoCity.tsx (MapViewer, lines 1546-1993; CityScene 1121-1425)

Problem

The campus / district / focus / interior mode lattice is one machine expressed as five useStates and ~15 derived expressions. Its precedence rule (expanded beats focus beats district) is re-derived independently in three places (L1616-1638, L1226-1253, L1847-1875), and "which anchor is current" is asked in four. The global Escape handler (L1820-1843) duplicates closeBuilding/closeFocus/closeDistrict instead of calling them. Every recent interaction bug (drill-down deselect, background-click re-anchor) was a fix to this lattice - and none of it is testable, because the decisions live in closures inside a component that requires mounting a WebGL <Canvas>.

Solution

A deep viewer/lib/navigation.ts module (pure reducer or hook over a reducer). Interface: current mode + selectedId out; select(id), explore(id), exploreDistrict(id), back(), deselect() in. It swallows closestVisibleAncestor, firstCampusConnection, connectionBetween, the precedence clamping, and the Escape policy. MapViewer, CityScene, and the overlay builders all read the same derived mode instead of re-deriving it.

Benefits

  • Locality: the precedence rule exists once; the next interaction bug is a one-file fix with a regression test.
  • Leverage: tests exercise the whole gesture grammar (double-click, background click, Escape, breadcrumb) through six functions - no WebGL, no jsdom canvas.
  • Testability: today the tested viewer surface is the props-in/DOM-out layer; the decisions layer is at 0%. This flips that.

2. Put the flow layout under test; share the sizing constants

Strong

Files: viewer/lib/flow-layout.ts (816 lines, 0% covered), viewer/RepoCity.tsx, vitest.config.ts

Problem

flow-layout.ts is already a deep module - four exports, type-only imports, fully deterministic, plain data in and out - yet it has zero tests. The blocker is accidental: the viewer test project only includes *.test.tsx, and the node project only includes test/**/*.test.ts, so the natural test file never runs. Meanwhile the module hard-codes the viewer's rendering knowledge by hand: the default footprint [1.65, 1.2, 1.4] appears in six places across both files, the plaque-width formula (flow-layout L491-497) is a verbatim copy of MapMarker (RepoCity L928-936), and flow-layout L620 asserts "structures draw at 80%" while RepoCity L622 actually uses 0.68 - a live drift the duplication has already caused.

Solution

(a) Admit test/unit/viewer/*.test.ts (or a lib glob) and characterise computeFlowLayout / createEdgeRouter through their existing interface - determinism, band ordering, the 600k-cell and 150k-expansion escape hatches, the throw paths. (b) Move the shared sizing constants (default footprint, render scale, plaque formula) into one exported module both files import, so the invariant is enforced by the compiler instead of by comments.

Benefits

  • Leverage: 816 lines of layout behaviour become assertable through two functions; the deepest untested module in the viewer gains a safety net at near-zero interface cost.
  • Locality: the 0.8-vs-0.68 class of drift becomes impossible - one constant, two readers.
  • Layout regressions (band overlap, router detours) get caught before an eyeball pass.

3. Give D17 (and D3) one home, per the catalogue's own convention

Strong

Files: src/lib/assemble-deployment-phases.ts L169-199, src/lib/assemble-overview-phases.ts L311-336, src/lib/inference.ts, src/lib/dockerfile.ts, src/lib/hosts.ts, src/lib/assemble-overview.ts L121-155

Problem

HEURISTICS.md states the convention: rules shared between the two map modes are implemented once in inference.ts with per-mode options. D17 violates it - external-service node and edge construction is written twice, and the edge payloads (kind: "data_flow", confidence: 0.7, label: "uses") are byte-identical duplicates whose ids differ only by a -u suffix. D3 is spread over five modules, with deployment and overview each applying an exclusion rule the other lacks (utility-room filter vs coarser-than-room-granularity skip). No module interface expresses "the two pipelines must agree"; only the golden test can notice a divergence, after the fact.

Solution

Move D17 node+edge construction into inference.ts as one function taking per-mode options (id suffix, parent strategy), exactly as M1/M8/M10 already do. For D3, extract a single COPY-attribution function that owns both exclusion rules explicitly, so the difference between the modes is a named option rather than two independent re-implementations. This is the same deepening the recent RFC-0002 dedupe applied elsewhere - finishing the job.

Benefits

  • Locality: the next D17 fix (like the delivers first-word fix, M10) lands once instead of twice.
  • Leverage: one unit test on the shared constructor covers both pipelines; byte-identity between modes becomes a property of the code, not of vigilance.
  • Restores the catalogue's stated architecture - HEURISTICS.md stops overclaiming.

4. Narrow the four golden-only assembly phases

Worth exploring

Files: src/lib/assemble-deployment-phases.ts (assembleHostDistricts L647, assemblePackageDistricts L1058, assembleDatabases L1493, assembleStaticClassification L524), src/lib/assemble-overview-phases.ts (assembleInfraDistricts L128)

Problem

The recent decomposition gave the pipelines named phases, but the four largest phases (340-370 lines each) are still only reachable through the golden end-to-end test. Their interfaces are wide - 15 to 19 options each, including three mutable side-channel sets (claimedSegments, serviceClaimedDirs, campusFileSets) written by one phase and read by another outside AssemblyState. Phase ordering is load-bearing (the nodeIds snapshot at L1437 decides database parenting) and enforced only by the literal call sequence plus comments. These phases fail the interface half of depth: enormous behaviour, but an interface nearly as wide as the implementation.

Solution

Not another decomposition - a narrowing. Move the three side channels into AssemblyState so all inter-phase data flows through one named object; have each phase declare what it reads and writes; and add direct unit tests to the four big phases the way the other eight already have them. The byte-identical golden invariant makes this mechanically safe (the recent 1468-to-400 extraction proved the workflow).

Benefits

  • Locality: "what does this phase depend on" becomes readable from its signature, not from tracing mutations.
  • Testability: the only producer of user-facing warnings (L1198, L1231) gains direct tests; ordering assumptions become assertable.
  • Reduces the risk in every future heuristic change to the D/M rules, which land in exactly these phases.

5. Extract the campus projection

Worth exploring

Files: viewer/RepoCity.tsx (isCampusNode L1574, visibleEdges L1601-1615, closestVisibleAncestor L553, firstCampusConnection L1699, connectionBetween L1718)

Problem

"Collapse the node/edge graph onto the currently visible level" is one idea implemented as five scattered pieces - all pure and three.js-free today, trapped in a component body, so the evidence-priority edge dedup (L1601-1615) and ancestor walk have no tests.

Solution

projectToVisible(map, visibleIds) -> { nodes, edges, ancestorOf, edgesTouching } in viewer/lib/. Natural companion to candidate 1 (the navigation machine consumes it) - if 1 proceeds, this likely falls out of it.

Benefits

  • Leverage: the dedup and ancestor rules become directly assertable with plain CityMap fixtures.
  • Locality: HC-011 (the deferred 5000-node overview problem) will need exactly this seam for any node-collapsing strategy - building it now is the enabling move, without touching HC-011 itself.

6. A text seam for the host-config scan

Speculative

Files: src/lib/host-config.ts (41% covered, no unit test file)

Problem

scanHostConfigs reads the filesystem directly, so every test needs a temp directory with a co-designed triple of YAML basenames, dirnames, and a Host[] vocabulary. Its uncovered 59% is exactly the subtle logic - the +/-4-line window suppression, the length-threshold gates, the fixed-point relaxation clamp in layerHosts.

Solution

Accept an injected reader (as complexity.ts already does at L35) or a (path) => text map, so tests feed text directly. compose.ts - string in, services out - is the house style to match.

Benefits

  • Testability: the threshold gates and relaxation clamp become reachable without filesystem scaffolding.
  • Speculative because the module changes rarely; do it when a D-rule change next touches it, not before.

Also noted, no card warranted: shallow pass-throughs that fail the deletion test - theme-toggle.tsx (one call site, props threaded through two levels), the local-showcases.ts type re-export, viewport-overlays.tsx (all six props fully computed upstream). Fold into candidate 1's cleanup if it proceeds; not worth standalone churn.

Top recommendation: candidate 2 first, then candidate 1

Start with 2 - it is almost pure gain: the deep module already exists with a clean four-export interface; the work is a test glob, characterisation tests, and one shared-constants module, and it fixes a live drift (the 0.8 vs 0.68 scale claim). It also builds the fixture vocabulary (small CityMap graphs) that candidates 1 and 5 will reuse.

Then 1 - the navigation machine is where the friction actually bites: the viewer is the active work area, the mode lattice is the source of the recent interaction bugs, and it is the largest body of untested decision logic in the codebase. Extracting it converts the next round of viewer polish from eyeball-verified to regression-tested, and candidate 5 falls out of it nearly for free.

Candidate 3 is the best generator-side move and can proceed independently at any time - it is small, protected by the byte-identical golden invariant, and finishes what RFC-0002 started.
